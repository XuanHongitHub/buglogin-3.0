# Profile and Proxy Unified Sync Design

Status: implementation contract; stale-assignment reads were aligned across REST/MCP/UI on 2026-10-17. Regression execution and hosted verification remain pending.

## Product behavior

- A profile owns its proxy selection through the canonical `Profile.proxy_id` reference.
- Proxy assignment changes are allowed only when a profile is `created`, `ready`, or `failed`. The API applies this rule both when staging an assignment and when activating it with a manifest; `launching`, `running`, `stopping`, and `recovering` are rejected so a transition cannot race browser startup, shutdown, or recovery.
- Reading a staged assignment returns it even when its expected profile revision is stale. The authorized owner needs the pending choice to inspect or restage it; sync activation still rejects stale revisions and never applies the stale choice.
- Production profiles use managed encrypted sync by default. Profile browser data, the canonical proxy assignment, and the referenced safe proxy metadata are one BugLogin API authority and one sync lifecycle; there is no profile or proxy sync toggle in the production desktop flow.
- Local-only profiles are limited to explicit development/local mode. Production UI must not present a local/disabled sync choice or claim cloud sync for a local-only profile.
- Profile metadata, profile browser data, and referenced proxy state use one BugLogin API authority, one versioned manifest, and one conflict/retry policy.
- A shared proxy referenced by multiple synced profiles has one canonical identity in the workspace. Manifests reference the workspace proxy ID and revision; safe metadata is read from the authorized canonical proxy API record and is not copied into each profile's object set.
- Proxy credentials remain profile/resource scoped: each manifest may reference an opaque encrypted credential envelope and an opaque `credentialVersion` from the canonical proxy record. The API validates both against the same-workspace proxy authority and authorizes the actor for it. The version is an identifier only, never secret material. A metadata-only proxy revision preserves it; replacing or clearing credentials changes/removes it. Legacy manifests without this field remain readable during the compatibility window.
- Proxy CRUD accepts an optional `hasCredential` marker in REST and MCP. On update, omitting it preserves the current credential and version; `false` clears both; `true` marks a credential replacement and rotates the opaque version. The API never accepts a username, password, or secret reference from the caller.
- Proxy updates are rejected while any active profile in the workspace that selects the proxy is running. The API repeats the check inside its serialized mutation so a concurrent launch cannot leave the running browser on a different configuration than the canonical proxy record.
- Proxy updates are also rejected while a pending profile assignment references that proxy. This keeps its selected revision and credentials stable until the matching manifest commit consumes the assignment; the check is repeated inside the serialized mutation.
- Profile DTOs expose the proxy ID and safe proxy metadata only. Credentials are encrypted on the client and stored in the OS vault; transport payloads contain only an opaque encrypted secret envelope/reference. Credentials never enter logs, audit detail, React, or MCP output.
- The resource key is wrapped by the profile recovery key. Encrypted direct sharing uses recipient-device HPKE envelope v2 to transfer both `ClientKey` and `RecoveryKey`, allowing the existing manifest decrypt and continued sync path. Until owner-side fingerprint confirmation/envelope creation and key rotation on revocation are complete, `profile.share` rejects encrypted profiles; metadata-only shares remain available.
- Recipient-device key wrapping uses HPKE RFC 9180 with DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and ChaCha20-Poly1305. The client envelope authenticates workspace ID, resource ID, recipient device ID, and the resource key-version fingerprint as AAD; it contains only the encapsulated public key and ciphertext. The receiver's private key stays in that device's OS vault. This cryptographic primitive does not itself establish the device-key directory or authorize sharing.
- The API key directory must bind each public key to an authenticated account/device session, persist changes with revision and audit, and expose only active keys for the target workspace member. Share must validate that every supplied envelope matches an active registered recipient device and the current resource key version before the ACL grant and envelope become visible together. Recipients may fetch only their own envelopes after current profile-read authorization; device-bearer identity, not a client-supplied device ID, selects the envelope.
- A signed-in account may select its own active membership as a recipient to provision the account's other active devices. This grants at member scope: every active device key is displayed and fingerprint-confirmed; the UI must not imply device-specific access.
- Encrypted direct-share wire shape: `ProfileShareInput.recipientKeyEnvelopes` is an exact set of `{ envelope, confirmedFingerprint }` entries. `ProfileKeyShareEnvelope` v2 HPKE-encrypts both the resource `ClientKey` and `RecoveryKey` (80-byte ciphertext) for the recipient device; v1 carried only `ClientKey` and cannot hydrate or continue sync. The API compares the confirmation with the fingerprint of the currently registered active device key, rejects duplicates/missing/extra devices, validates the envelope scope and key version, then commits grants and envelope records in the same versioned control aggregate. The recipient GET route derives device ID from the authenticated device-bound bearer and returns only that device's envelope after the current hosted profile-read check. Metadata-only sharing sends an empty list. The API never accepts a caller-selected device identity for retrieval.
- The initial directory trust anchor is the authenticated device session over the configured HTTPS API. The client must display the recipient device-key fingerprint during sharing and require an owner-visible confirmation before wrapping. The API never receives a private key or resource key. The owner remains responsible for verifying the recipient fingerprint through a trusted channel; API TLS and ACL authorization do not prevent a compromised API from substituting a public key.
- Revoking a share removes that recipient's ACL and future envelope access immediately. Since a recipient may already have copied plaintext or a resource key, revocation cannot erase past knowledge. Before any remaining recipient can resume reading new sync generations, the owner device must rotate the resource key, re-encrypt all live objects, publish a contiguous fresh manifest with no old-key object reuse, and create new envelopes only for remaining active devices. Until that rotation commits, the API must report a rotation-pending state and deny sync reads/launches that would rely on the old shared key. A crash or failed rotation leaves the resource locked for retry; the old manifest stays available only to the owner recovery workflow, not to revoked members.

## Sync efficiency

- Profile snapshots exclude regenerable Chromium cache and crash-dump directories (`Cache`, `Code Cache`, `GPUCache`, `GrShaderCache`, `DawnCache`, `ShaderCache`, `ScriptCache`, `Media Cache`, `Crashpad`, `Crash Reports`, and `crash_reports`) at every nesting level. The same filter applies when staging legacy profile data, so caches are not cloned or uploaded; persistent browser state such as `Cookies`, `Local Storage`, `IndexedDB`, service-worker state, and extensions remains in scope. Excluded paths disappear from the next manifest and are tombstoned by the normal generation commit. Existing manifests containing cache paths remain readable and idempotently replayable; only a new base or successor write is rejected if it introduces those paths.
- Use manifest generations, ETags/revisions, idempotency keys, and content hashes to skip unchanged blobs. Proxy metadata is canonical workspace state and is not a profile sync blob.
- Send only changed profile metadata, proxy configuration, and browser-data chunks. Do not re-upload an entire browser-data directory when a small set of files changed.
- The v1 profile projection is not incremental: its AES-GCM associated data includes the manifest generation, encryption uses a fresh nonce, and the API's physical blob key includes that generation. Re-encrypting unchanged file bytes therefore creates a new object and a full upload. New v2 payloads use stable workspace/resource/path associated data and publish a key-version fingerprint; v1 remains readable. The desktop authenticates cached ciphertext against the current plaintext even when the prior manifest does not contain it, so an interrupted pre-activation retry can reuse the same ciphertext; it sets `sourceGeneration` only when the exact object exists in the prior manifest. The API permits exact immutable-object reuse from the immediately previous manifest. Bounded per-object upload concurrency is implemented; remote partial-file resume and staging proof remain outstanding. The standalone `sync::chunks` utility uses stable logical chunk associated data and ciphertext-addressed keys, but the profile projection does not use it yet.
- A v2 manifest object may declare `sourceGeneration` to reuse an immutable object. The API accepts it only when the immediately previous active manifest contains the exact key, size, checksum, physical source generation, and same resource-key version. The API resolves the prior physical generation internally; clients cannot provide arbitrary object-store keys. A key-version change is accepted only as a contiguous generation with a changed resource-key envelope, no reused objects, and every prior object either re-uploaded or tombstoned. The API cannot inspect client keys or prove ciphertext was encrypted with the declared key; clients must verify key fingerprints and authenticate every downloaded object.
- Coalesce rapid edits per profile, bound transfer concurrency and chunk size, and resume verified chunks after interruption. Desktop profile blob requests use a fixed concurrency ceiling of four; each object remains independently checksummed, encrypted, and idempotent, and manifest activation waits until every changed object has a successful receipt. Production S3 storage operations no longer share an API-wide mutex; legacy adapters remain serialized for compatibility. This does not claim resumable partial-file transfer or a measured production throughput gain: the profile projection still uploads a changed file as one encrypted object.
- A profile blob presence check is scoped by workspace/resource ACL, active write lease/fencing token, generation, object key, and ciphertext checksum. It may skip retransmitting a complete staged blob after an interrupted upload, but it does not expose arbitrary storage keys, confirm other resources' objects, or replace manifest activation. The check is advisory; immutable checksum-addressed PUT remains idempotent if the blob changes or disappears between check and upload.
- After the browser process stops for snapshot/upload, the desktop keeps renewing that profile's write lease until manifest activation succeeds or the application shuts down. A stopped process alone is not a reason for the runtime heartbeat to release the lease. Transfer or finalize failure leaves the committed manifest unchanged and retains retry state so the same stopped profile can retry; runtime cleanup releases the lease during shutdown.
- Profile start/stop and proxy edits must not trigger redundant full scans. Maintain a local change journal or equivalent incremental manifest input, with periodic reconciliation as recovery.
- Enforce per-file and per-profile size limits at the API boundary and return typed quota/validation errors before accepting partial state.
- Use one shared 64 MiB encrypted object limit in the Rust manifest validator, HTTP upload body extractor, and desktop snapshot. Per-profile/workspace aggregate quotas remain enforced separately by workspace usage policy.
- A profile and its proxy dependency become visible atomically at one manifest generation. Missing, unauthorized, stale, or cross-workspace proxy references reject the commit without changing the active profile revision.

## Draft manifest dependency contract

- `SyncManifest.dependencies` is an additive array; older manifests deserialize with an empty array.
- `SyncManifest.payloadEncryption` is an optional versioned declaration for backward-readable manifests. New commits containing payload objects require `schemaVersion: 1`, a supported v1/v2 algorithm, and the canonical resource key-envelope reference at `.buglogin/resource-key-envelope.json` in the same manifest object set. New desktop writes use v2 and include `keyVersion`; v1 remains readable. Each profile/resource has a distinct AES-256-GCM key. Proxy metadata stays safe and explicit as a manifest dependency; the envelope is never projected into browser user data.
- Profile payload objects use the authenticated chunk wire format. The API rejects raw profile blobs before storing them, then checks the declared algorithm, resource-envelope JSON shape/workspace+resource scope, and chunk framing before activation. The server has no key and cannot verify an AES-GCM tag; clients must authenticate every chunk before use.
- Payload encryption v1 binds associated data to workspace, resource, generation, and path. V2 binds to workspace, resource, and path so an unchanged ciphertext can be reused across generations. Its `keyVersion` is the SHA-256 fingerprint of the 256-bit resource key; clients verify it after recovery. The API enforces a full fresh-object generation when this key version changes, but desktop key generation, vault replacement, recovery-code UX, and rotation/revocation orchestration remain required before the rotation capability can ship.
- A proxy dependency contains `kind: "proxy"`, canonical `proxyId`, metadata `revision`, optional opaque `credentialVersion`, and profile-scoped credential envelope reference. The API compares `credentialVersion` with the canonical proxy record whenever the manifest is current. Metadata-only revision changes preserve the version; credential replacement creates a new version and requires a fresh envelope on each synced profile/device before that generation activates.
- The API validates that every dependency belongs to the same workspace, is referenced by the profile's canonical `proxy_id`, is readable by the actor, and has a current proxy revision before manifest activation. It validates the proxy-envelope workspace/resource/proxy/revision scope and encrypted wire version both at blob upload and manifest activation.
- A profile with no selected proxy must have no proxy dependency. A profile with a selected proxy must have exactly one matching dependency. Duplicate, stale, missing, unauthorized, and cross-workspace dependencies reject the entire generation.
- Credential envelopes are opaque to the server. A missing, revoked, or wrong-device key must not be treated as a usable proxy credential.
- The Rust sync crate implements the v2 HPKE profile-key envelope with device-bound scope checks and tamper tests. It wraps both the client and recovery keys required by the existing encrypted manifest lifecycle. The API persists immutable public keys registered by authenticated device sessions, offers an authorized query of active recipient-device keys, and stores/retrieves per-device envelopes atomically with grants. Desktop OS-vault enrollment and recipient envelope retrieval/persistence are implemented. Owner fingerprint confirmation/envelope creation, authenticated replay/no-leak coverage, completed revoke/rekey delivery, and hosted persistence evidence remain open; encrypted profile sharing must continue to fail closed until these layers are verified together.
- The Rust `ProxyCredentialEnvelope` wire type uses schema version 1 and AES-256-GCM with the profile resource key. Its authenticated data is `buglogin/proxy-credential/v1/{workspaceId}/{resourceId}/{proxyId}/{proxyRevision}`; opening requires every scope field and revision to match the active manifest dependency. The credential bytes are JSON `{username,password}` and must remain in Rust/OS vault after decryption, never in the browser profile directory, React, operation results, or logs.
- Object bytes remain invisible until the PostgreSQL manifest activation commits. Retries with the same idempotency key and request hash return the original receipt; conflicts preserve the prior active generation.
- Hosted REST and MCP reads refresh the PostgreSQL control aggregate and hold a read snapshot gate through authorization and response selection. Mutations through both surfaces take the matching write gate. A request must not authorize against one aggregate revision and return a profile, proxy, ACL, manifest, blob, or audit record selected from another local revision.
- The read gate checks the durable aggregate revision first and deserializes/rebuilds the in-memory aggregate only when the revision changed; unchanged reads must not repeatedly decode the full JSONB control record.
- The desktop stores each resource data key and recovery key together as one secret in the OS vault. The recovery key wraps only that resource key in the manifest envelope, preserving profile-level ACL boundaries. Tauri exposes an authenticated recovery-code read and recovery operation. Recipient envelope v2 now carries both keys under recipient-device HPKE and launch can retrieve/persist it; owner fingerprint review/envelope publication, key rotation/revocation completion, and durable audit evidence remain required before encrypted profile sharing can ship.

## Large profile-file chunk protocol

- Preserve manifest schema v2 byte/behavior compatibility. Add schema v3 only for generations that need a file split across multiple encrypted objects; old clients must reject v3 rather than misproject it.
- A v3 manifest adds a sorted `fileChunks` table. Each entry binds one confined logical profile path to the plaintext byte length and SHA-256 checksum, plus ordered per-chunk references (index, plaintext length/checksum, and the exact ciphertext object key/length/checksum). The `objects` list remains the authoritative immutable remote object set; the table may reference only objects listed there, and a chunk object may be referenced exactly once.
- Keep files at or below the current single-object limit in the existing representation. Split only larger files into fixed 4 MiB plaintext chunks, encrypted client-side with stable AAD bound to workspace, resource, logical path, chunk index, and plaintext checksum. Use ciphertext-addressed immutable keys. Empty files stay representable as existing single objects.
- API validation must reject unsafe/duplicate logical paths, non-contiguous indices, inconsistent aggregate lengths, invalid checksums, missing/duplicate/unreferenced chunk objects, unsupported encryption, and quota violations before manifest activation. It verifies ciphertext object receipts and structural metadata; only the client can verify AES-GCM tags and whole-file plaintext checksums.
- The canonical root must bind both the encrypted object set and the sorted file-chunk table. Hydration authenticates each chunk, checks per-chunk and aggregate checksums/lengths, stages the complete profile generation, and publishes it only after every file passes.
- Reuse unchanged chunks only when their exact ciphertext object exists in the immediately previous manifest under the same resource key version. Cache authenticated ciphertext by workspace/resource/key-version/path/index/plaintext checksum so retries do not re-encrypt unchanged chunks with a new nonce. Manifest activation remains the final atomic visibility point.
- Migration export/import preserves v2 manifests unchanged; v3 fields now flow through the same typed manifest/export structures, but a v3 migration round-trip test is still required. Desktop snapshot encryption/cache/hydration has initial local v3 support, but it materializes file bytes in memory. Streaming/coalescing, interrupted transfer, and restart recovery require end-to-end tests before this protocol is production-ready.

## Authority and security

- Rust owns sync scheduling, proxy/profile serialization, hashing, chunk transfer, retries, conflict decisions, secret encryption/decryption, and API credentials.
- The hosted API owns workspace ACL, canonical profile/proxy IDs, resource bindings, leases/fencing, revisions, quotas, audit, and atomic manifest activation.
- The hosted API enforces `WorkspacePolicy.maxStorageBytes` against aggregate committed manifest object bytes when activating a manifest. Client-reported `WorkspaceUsage` is advisory and cannot authorize storage. An already over-quota workspace may reduce or retain a resource footprint, but may not grow it further.
- Browser clients use one configured web origin. The API answers credentialed CORS and preflight only for that exact origin and canonical API methods/headers; wildcard origins are forbidden.
- The server must validate the actor's access to both profile and proxy in the same workspace on every read/write; client-side UI state is not authorization.
- Direct object reads must revalidate the current manifest's proxy dependency ACL and revision before returning any blob. A previously observed immutable object key must not bypass revoked proxy access.
- Stale-proxy repair is an explicit read path: manifest and blob repair reads require both `profile.read` and `profile.update`; the API still checks the profile's current proxy selection and the caller's current access to that canonical proxy. It only tolerates the old proxy revision during re-encryption and grants no launch or commit authority.
- Production mode never falls back to Donut endpoints or local files as authority when BugLogin API is unavailable. Existing local/self-host mode remains explicit and isolated.
- Proxy credentials are not silently copied between workspaces or devices. A device lacking the required secret key reports an actionable missing-secret state and cannot launch through that proxy.
- Parsed proxy usernames/passwords, raw pasted import text, and credential-bearing request JSON must be zeroized on drop, including early error paths; credential-bearing `Debug` output remains redacted, and credentials are persisted only through the OS vault and encrypted profile envelopes.

## Compatibility and migration

- There is no current per-proxy `sync_enabled` field or UI toggle to migrate. Legacy `sync_enabled` fields found in the importer belong to VPN/extension formats and must retain their own semantics; do not reinterpret them as proxy sync state.
- The migration must not automatically upload every stored proxy. Only dependencies of profiles the user or workspace has explicitly enabled for hosted sync are eligible.
- Do not add an independent proxy sync toggle; proxy state follows the profile's canonical proxy assignment and manifest dependency.
- Preserve local proxy use in local mode. A remote API outage must not delete local profiles or proxy credentials.

## Required contract additions before hosted implementation

- Profile/proxy CRUD and profile-to-proxy binding under workspace-scoped authorization.
- Atomic profile-manifest commit that validates proxy dependency revision(s).
- Proxy credential envelope format, device key lifecycle, rotation, revocation, and recovery behavior. The v1 envelope wire type, projection serialization/hydration, REST/MCP metadata marker, API object-scope validation, launch bridge consumption, and local OS-vault input/snapshot wiring exist. Staging verification and key lifecycle remain unproven. Recipient-key distribution for profile sharing is not implemented; encrypted-profile sharing now fails closed until it is.
- Incremental blob transfer protocol with chunk checksums, resume semantics, quota errors, and idempotent finalize.
- ACL, audit, lease/fencing, conflict, idempotency, and error mappings shared by Rust, REST/OpenAPI, and MCP.
- Staging contract tests and Windows/macOS device-vault evidence.

The existing `production-launch-sync-v1.yaml` is a draft dependency and lease contract. It does not currently define immutable proxy objects, proxy-secret envelopes, or atomic profile-plus-proxy activation. Do not wire endpoint behavior or claim this feature production-ready until the contract is versioned and verified against staging.
