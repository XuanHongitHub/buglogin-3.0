# Legacy Hosted Profile Migration Design

## Problem

BugLogin 1.0 stores hosted profile metadata in PostgreSQL and browser/profile state in separate sources. The current migration package builds profile entities only from local `profiles/<uuid>/metadata.json`, while the control-plane exporter builds bindings from share grants. This leaves active grants pointing at profiles absent from the local snapshot and can make an otherwise valid ACL graph unpackageable.

## Contract

- The 1.0 `workspace_profiles` rows are authoritative for every hosted profile's identity, workspace, display metadata, runtime, proxy, group, and lifecycle timestamps.
- Every hosted profile gets exactly one deterministic 3.0 profile record, resource record, and profile-resource binding, whether or not it has a share grant. Share grants reference that same resource.
- For a profile also present in the local snapshot, preserve its authenticated profile data and non-secret runtime configuration while taking shared metadata and workspace relationships from the PostgreSQL row.
- For a profile with metadata but no verified profile payload, retain the record as `migration.preserve-only` with an explicit excluded-data reason. It must not become launchable as an empty profile.
- An unsupported legacy browser runtime must not abort the whole one-pass control import. Keep its original runtime label and sanitized legacy configuration in migration metadata, store the active profile with a non-launchable `preserved` runtime sentinel, and keep it in `Created` state. Normal profile creation must reject this sentinel; desktop launch must fail closed until a real adapter is installed and an explicit conversion is performed.
- Hosted browser state must enter 3.0 through the existing desktop profile projection and per-resource `ClientKey`/`RecoveryKey` flow. The migration API must never decrypt or re-encrypt browser files with a server-side migration key. Legacy cookies remain ordinary profile files and receive the same client-side encryption as other profile state.
- A migrated profile is launchable only after its verified local files have been imported into the projection and the normal sync commit has activated the encrypted successor manifest for the deterministic resource binding. The empty genesis manifest created during control provisioning is not evidence that legacy browser data has been migrated.
- The migration flow imports the hosted control graph first, then the Tauri-only `migration.profile.data.import` operation walks the prepared source tree and imports each hosted profile through its active binding. It uses active manifests as per-profile receipts, so retries skip committed encrypted generations and never roll back earlier profiles.
- The desktop migration operation is governed by `profile.update` / `Action::Update`, matching the authorization required by the normal sync manifest/blob writes; each profile remains independently authorized by the hosted sync API.
- A new empty 3.0 candidate has no authenticated `migration.write` principal yet. Seed its first migrated account graph with a local Rust operator command that verifies the signed migration package, constructs the production API state from the protected service environment, and calls the same Rust control-import service. Run it under the dedicated BugLogin service identity; it must not connect by direct SQL or expose an unauthenticated HTTP route. Require the package to contain a password-capable legacy platform administrator, write the normal migration audit/journal, and make replay idempotent. The imported administrator then signs in with the migrated credential and performs all later migration actions through authenticated REST/Tauri.
- The initial signed package is control-only: it carries profile metadata and encrypted account/proxy/VPN secrets but an empty encrypted-profile-data index. It must omit browser payload bytes so the small VPS never loads the 354 MB profile set into the API process. The authenticated desktop importer streams those bytes later through normal sync.
- Provision the matching migration encryption/signing key pair with a Rust operator command backed by the native OS vault. The command may write a short-lived service-environment handoff file only to a caller-selected protected local path, must never print key values, must refuse overwrite/reuse, and must remove newly created vault entries if handoff-file creation fails.
- Keep regular package upload/verify/activate endpoints restricted to the authenticated `migration.write` capability. The local operator import is only for the signed, initial migration into the isolated empty candidate; it refuses existing account/identity state unless resuming the same package journal.
- The desktop importer stages each legacy tree atomically as dirty local data and passes it through the ordinary lease, projection snapshot, encrypted blob upload, and manifest commit path. It does not trust source bytes as a completed projection generation or create a `SyncExport` by re-encrypting data on the API.
- Never infer missing IDs, workspace relationships, runtime artifacts, or proxy credentials. Duplicate IDs, cross-workspace conflicts, invalid runtime fields, or conflicting resource bindings stop export.
- Active profile-share rows whose profile is absent or belongs to another workspace are preserved with hashed recipient identity as `orphaned_profile` provenance only; they are never imported as active grants. This retains the source row while avoiding permissions on a nonexistent or mismatched resource.
- Share rows addressed to a platform administrator are preserved with hashed recipient identity as `platform_recipient` provenance only. Platform administrators keep platform-level authority and do not receive synthetic workspace memberships or redundant resource grants.
- Unsupported and unknown runtime names are not converted to a supported engine. They remain visible/recoverable as preserved records and do not prevent supported profiles, ACLs, and workspaces from being cloned.
- Raw `bugox_config` / `bugium_config` JSON and secret-bearing fields are not added to the control-plane export.

## Boundaries

The PostgreSQL exporter remains a repeatable-read, read-only transaction reached through an authenticated loopback tunnel. The S3 hydrator performs GET-only reads of the workspace/profile manifest and file objects. It validates profile/workspace identity, path safety, declared size, and legacy BLAKE3 before writing to the prepared local source. Invalid remote data uses an existing non-empty local payload or leaves the profile preserve-only. S3 writes are never part of this flow. Support for the `bugox` / `cloak` runtimes remains a separate activation gate; a path-ID match alone does not mark browser data as migrated.
